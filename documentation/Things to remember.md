# Things to Remember — Ludio Game Engine

## 1. JSON Structure, Setup & Flow

- **Architecture:** A game JSON has distinct sections: `gameInitOptions`, `visualSettings`, `beforeLoopActions`, `gameLoop`, `winCondition` (or `playersWinCondition`), and `postGameActions`. If players can become spectators (i.e. leave mid-game) or spectators can become players (i.e. join mid-game), there are also sections for `turnPlayerToSpectatorActions` and `turnSpectatorToPlayerActions`.
- **beforeLoopActions Limitations:** This is a simple list of actions, NOT action groups. You CANNOT use `repeat` or `parallel` modifiers here. Do all deck creations (`createCustomDeck`, `createDeck`) and array initializations here so they execute only once.
- **`createGenericCardWidget` Placement:** Never call `createGenericCardWidget` before the tutorial group, and never before all decks referenced in its `"decks"` field have been created via `createDeck`/`createCustomDeck`. Since position decks (created with `repeat`) must live in the first `gameLoop` group, `createGenericCardWidget` must also be in the `gameLoop` (with `skipCondition: gameLoopIndex > 0`), placed after all deck-creation groups.
- **`repeat`/`parallel` Must Be Top-Level on Action Groups:** A `repeat` or `parallel` block modifies an action group — it is a top-level key alongside `"name"`, `"actions"`, and `"skipCondition"`. It CANNOT appear as an item inside an `actions` array (i.e., nested inside another group's actions). If you find yourself placing `{"repeat": {...}, "actions": [...]}` inside a list of actions, extract it into its own top-level action group in the `gameLoop`.
- **beforeLoopActions for One-Time Setup:** Any setup that only needs to run once (e.g., `createDeck`, `createCustomDeck`, `createVideoboxDecks`) should live in `beforeLoopActions`, NOT in a `gameLoop` group with `skipCondition: gameLoopIndex > 0`. The only exception is when the setup requires a `repeat` or `parallel` block (which cannot be used in `beforeLoopActions`) — in that case, put it in the first `gameLoop` group with `skipCondition: gameLoopIndex > 0`. For example, creating decks with dynamic player-name labels requires a `repeat`, so those stay in the game loop; but creating fixed-name decks and `createVideoboxDecks` all belong in `beforeLoopActions`.
- **Dynamic Setup:** If you need dynamic setup based on player count that requires `repeat`/`parallel`, do it in the first group of the `gameLoop` with a `skipCondition` of `gameLoopIndex > 0`.
- **`setImagesRow` Placement:** Place `setImagesRow` (the transparent image row that makes space for the card hand) in `beforeLoopActions`, after any pre-game votes or notifications that shouldn't show the hand area yet. This ensures the hand space is visible from the moment actual gameplay begins.
- **Score Initialization:** Player scores default to 0 at game start. Never call `updateScore` to initialize scores to 0 — it is unnecessary.
- **`isActionLoop` is Free Inside Loops:** Within any loop (including `[]` nested loops and the outer `gameLoop`), Ludio provides `isActionLoop` as `true` automatically. Never initialize it to `true` in `beforeLoopActions` or anywhere else — only set it to `false` when you want to exit the loop. Do NOT add `isActionLoop` as a field on an action group object — it is not a valid group field and the validator will flag it.
- **Action Group Allowed Fields:** Action group objects (the entries in the `gameLoop` list) may only contain these fields: `name`, `repeat`, `parallel`, `skipCondition`, `actions`, `checkWinCondition`, `turnPlayersToSpectators`, `turnSpectatorsToPlayers`. Any other field (e.g. `isActionLoop`, custom metadata) is invalid and will be caught by the validator.
- **`turnPlayersToSpectators` / `turnSpectatorsToPlayers` Flags:** Place these two flags on a dedicated empty action group at the end of the `gameLoop` (e.g. `{"name": "Change players", "turnPlayersToSpectators": true, "turnSpectatorsToPlayers": true, "actions": []}`). This marks the safe point in the loop where player↔spectator transitions can occur. Do not scatter the flags across other groups.
- **Individual Actions Can Have `skipCondition`:** Not just action groups — individual action objects inside an `actions` array can also carry a `skipCondition` array. This is useful for skipping one notification within a group based on a result computed earlier in that same group (e.g. skip the "success" notification if the outcome was failure), without needing to split the group into two separate conditional groups.
- **`inc`/`dec` for ±1:** Use `inc(arg)` and `dec(arg)` (single param named `"arg"`) instead of `add(x, 1)` / `subtract(x, 1)` when incrementing or decrementing by 1.
- **showScore Placement:** `showScore` should typically be called in `beforeLoopActions` so the score display is visible from the very start of the game.
- **Game Loop Execution:** The `gameLoop` is a list of action groups (objects or arrays for nested loops). It repeats until `playersWinCondition.gameOverCondition` evaluates to true. To skip an action or action group, use a `skipCondition` that evaluates to a boolean.
- **`nextGroupNonStop` is default true:** Never include this field — it is redundant. Only set it explicitly if you need `false`.
- **Dot Notation for List Access:** When a selector param needs a specific element of a cached list by hardcoded index, use `{"name": "argN", "type": "cached", "value": "listName.0"}` instead of wrapping it in a `selectElement` selector. Only use `selectElement` when the index is itself computed or cached (dynamic). Note: this shorthand only works as a param `value` inside a selector, not as a direct `saveValueInCache` entry value.
- **Never Repeat Actions with skipConditions When a Variable Already Holds the Value:** If you have a cached variable (e.g. `selectedTrickDeck`, `winnerSuit`) that already holds the value you need, pass it directly into the action payload via `cached` — do not write N copies of the action each hardcoding one possible value with a `skipCondition` guard. One action, one cached reference.
- **Cache Repeated Computations:** If a selector expression is used more than once, compute it once in `saveValueInCache` (or `beforeLoopActions`) and reference the cached variable everywhere else. Within a single `saveValueInCache` block, order entries so that later entries can reference earlier ones — e.g. compute `currentPlayerIndex` first, then `currentPlayer = selectElement(players, currentPlayerIndex)`. Wherever `numPlayers` is recomputed (spectator transitions, round resets), also recompute any derived cached lists that depend on it.
- **Boolean "Update" Flag Pattern:** When you need to update both a "highest rank" and a "highest player" variable in the same `saveValueInCache` block, compute a single boolean flag first (e.g. `isHighestTrump = suit == trump AND rank > highestTrumpRank`), then use that flag as the `condition` in both the rank update and the player update. Never re-compute the condition inline in each `ifElse` — by the time you compute the player, the rank has already been updated and the inline condition will compare against the wrong value.
- **Idiomatic Double Loops:** Nested loops automatically restart at the top of their bracket unless a cached variable `isActionLoop` evaluates to false. If you need a nested loop, wrap the outer loop in square brackets `[]` (which provides a native `loopIndex` variable). Inside that bracket, use an `emptyAction` to evaluate an `isActionLoop` boolean to natively break out of the outer loop, and use a `repeat` block for the inner loop. You do not need to add `skipCondition: isActionLoop == false` to subsequent actions inside the bracket; the engine handles the exit automatically.

## 2. Payloads & Selectors (Strict Syntax)

- **Payload Types:** Actions take inputs in their payload divided into `preset` (primitives), `cached` (variables saved to cache), and `computed` (values derived dynamically using selector functions). Selector functions include `ifElse`, `listLength`, `incObjectFieldValue`, `getPlayersWithMaxScore`, `listsSubtract`, etc.
- **No "preset" Selector:** There is no selector called `"preset"`.
- **Don't Wrap Already-List Variables in `createList`:** Before using `createList` with a single cached argument, verify that the variable is a scalar. If the variable is already a list (e.g. built with `concat`, `ifElse` returning a list, etc.), reference it directly via `cached` — wrapping it in `createList` creates a list-of-lists and causes errors. To save a literal value to cache, write it directly: `{"name": "myVar", "value": 0}` or `{"name": "myList", "value": [1,2,3]}` or `{"name": "myDict", "value": {"a": 1}}`. Similarly, static values in a payload belong in the `preset` block, not in `computed` with a fake selector.
- **Strict Param Structure:** Inside a selector, EVERY item in the `params` list MUST be an object with exactly three keys: `"name"`, `"type"`, and `"value"`. Never use shorthand.
- **Eager Evaluation Trap:** In an `ifElse` selector, Ludio computes BOTH the `thenValue` and `elseValue` regardless of the condition — there is NO lazy evaluation. You must never use `ifElse` to guard an expression that would be invalid in one branch (e.g. accessing an index that doesn't exist in a smaller list). Both branches are always evaluated, so an invalid sub-expression will crash or produce wrong values even if the condition would "skip" it. Design expressions so every branch is safe to evaluate unconditionally — for example, use `remainder` or `minValue` to clamp indices rather than relying on a condition to prevent out-of-bounds access. Similarly, never evaluate the index of a list that might be empty.
- **Safe Lookups & Manipulation:**
  - Always use the `defaultValue` field with the `getCachedObjectValue` selector so the engine doesn't crash if the key doesn't exist yet.
  - NEVER use the `equals` selector to compare booleans. To check if a variable is true, use `getCachedValue`. To check if it is false, use the `logicalNOT` selector.
  - NEVER use `equals` to compare two lists — it only works on primitive values (integers, strings, booleans). To compare two lists, wrap each side in `listToString` first and compare the resulting strings: `equals(listToString(list1), listToString(list2))`.
  - `getCachedValue` takes exactly one param: `{"name": "name", "type": "preset", "value": "<variableName>"}`. The param name is literally `"name"` — never `"fieldName"` or anything else.
  - Use the native `inc` and `dec` selectors (which take a single `"arg"`) instead of using `add`/`subtract` with 1.
  - Use `negate` (takes one param `"arg"`) to return the negative of a number, instead of `subtract(0, x)`.
  - In `getCachedObjectValue` and `setCachedObjectValue`, the `objectName` param is the literal name of the cache variable (a string you can write directly), so it is almost always `"type": "preset"`. Only use `"type": "cached"` if the object name itself is stored in another variable.
  - `logicalAND` accepts an unlimited number of arguments (`arg1`, `arg2`, `arg3`, …). Never nest `logicalAND` inside another `logicalAND` — flatten them into one call with N args instead.
- **Strings in Computed:** If formatting a string to determine a dynamic target (e.g., `"videobox_($1)"`), it MUST go in the `computed` block, never the `cached` block.
- **Any Payload Field Can Be Computed:** Every field in an action's `preset`, `cached`, or `computed` section can be replaced with a computed selector. In particular, for actions with binary outcomes (success vs. failure), use a single action with `ifElse` on `sounds.list`, `image`, `header`, `text`, etc. rather than two separate conditional actions. For example, a result notification can compute `sounds.list` as `ifElse(correct, ["soundboard.success"], ["soundboard.failure"])` — one action covers both paths cleanly.
- **Prefer `type: "cached"` Over `getCachedValue` in Params:** When a selector param needs to reference a cached variable, always use `{"name": "...", "type": "cached", "value": "varName"}` — never `{"name": "...", "type": "computed", "value": {"selector": "getCachedValue", "params": [{"name": "name", "type": "preset", "value": "varName"}]}}`. The `getCachedValue` selector wrapped in `type: "computed"` is redundant and verbose; `type: "cached"` is the correct and concise form. The only place `getCachedValue` is valid is as a top-level value in a `computed` payload field (not inside a params array) or in a `skipCondition` entry.
- **Use `players` Not `allUsers` for Notification Targets:** Spectators automatically receive a copy of all notifications, so using `{"selector": "allUsers"}` as the `to` field of a `createNotification` (or the `labelInspectors` field of `setLabelInspectors`) is redundant. Always use the cached variable `players` instead. Move the field from the `computed` section to the `cached` section: `"cached": {"to": "players"}`. The same applies to `playList.0` for sounds and any other audience field — target `players`, not `allUsers`.

## 3. Cards & Actions

- **Never Create Player-Count Aliases:** Do not create variables like `players4` that pad `players` to a fixed length to work around player-count differences. Always use `players` directly. When an action must be performed once per player (e.g. dealing each player their own copy of a deck), use a `repeat` block with `qnt: numPlayers` and `formatString` to derive the deck name dynamically via `repeatIndex`. This is both player-count-agnostic and avoids the duplicate-card bug caused by padding.
- **One Cards JSON Per Game:** All card types for a game (playing cards, bid cards, special cards, etc.) should live in a single cards JSON file. Only split into a separate file if the cards are genuinely reusable across multiple games (e.g., a shared `bids_cards.json`). Game-specific card types always belong in the main cards JSON.
- **Deck Labels Go on `createCustomDeck`, Not on `createCard`:** The `label` field on `createCustomDeck` labels the deck itself (shown in the widget). Fields in a `createCard` payload become attributes of the individual card, not the deck. Always set the player-name label in `createCustomDeck`. Because player names are unavailable in `beforeLoopActions`, create labeled decks in the first `gameLoop` group (with `skipCondition: gameLoopIndex > 0`) using a `repeat` block with `getPlayerNameById` as the label.
- **dealDeck Rules & Safety:** `dealDeck` is the ONLY action used to move cards from a deck to a player's hand. You MUST specify a `qnt` (quantity), or the engine will vacuum up the entire deck. Always sort `dealDeck` by `weight asc`. Always check if a deck has cards before dealing from it, skipping the action if it is empty. If drawing a dynamic amount, use the `minValue` selector to ensure you don't draw more cards than exist in the deck.
- **Other Card Movements:** `moveCards` (type: `"deck"`) is strictly for moving cards DECK-to-DECK. `moveCards` (type: `"hand"`) is for moving cards HAND-to-HAND. `recallCards` is strictly for moving cards from a player's HAND to a DECK. The `targets` field of `recallCards` accepts either a single player ID string OR a list of player IDs — pass all players at once when the same recall applies to all of them, rather than looping one player at a time.
- **playCards Rules:** Do not use `oneClick: true` if the action requires playing more than 1 card. You do not need to remove/restore the central widget just to play cards. Always include `"playable": "availableCards"` in the preset payload. The correct postHandler is `"playOneRandomCard"` and it must be a top-level field on the action, not inside the payload.
- **postHandlers Placement & Usage:** `postHandler` is always a top-level field on the action object, never inside `payload`. Use `playOneRandomCard` for `playCards` actions. For `selectCentralWidgetDeck`, omit the postHandler entirely if the "nothing clicked" case is handled in `saveValueInCache`.
- **createGenericCardWidget Must Precede playCards and selectCentralWidgetDeck:** The prompts for `playCards` and `selectCentralWidgetDeck` are displayed inside the central widget. Call `createGenericCardWidget` in a dedicated setup action group that runs before any `playCards` or `selectCentralWidgetDeck` action — even if those actions are in a bidding phase that precedes the trick loop. Do not rely on the widget being created inside the trick loop if bidding happens first.

## 4. Voting, Targeting UX, & Interactions

- **createVote Requirements:** Must ALWAYS include `title`, `type`, `question`, `terminationCondition`, `actors`, and `showResultInRealTime` — all six are mandatory and the validator will flag any that are missing. `question` must be in the `computed` block (usually a `formatString` mentioning the actor's name). `showResultInRealTime` is a boolean preset (usually `true`). Use `oneClick: true` to let players click targets without needing a second confirmation click.
- **Lists for Actors/Targets:** Actions like `createVote` or `createNotification` require the `actors` or `to` payloads to be lists. Use the `createList` selector to wrap a single player ID.
- **Targeting via Decks:** Instead of using `createVote` to target a player, it is often better UX to use `selectCentralWidgetDeck` to let a player click on their target's public discard deck to inspect the field. This action returns a dictionary of `{userId: deckId}`. Safe targeting requires subtracting a player's own decks from the clickable pool so they cannot click themselves.
- **Input Parallelism:** The `createInput` action is natively parallel. If you set `actors: "players"`, everyone gets their own input box simultaneously. It outputs a dictionary mapping player IDs to their submitted strings to `lastActionResult`. Do not wrap `createInput` in a parallel action group.
- **`createInput` `scope` and `private`:** The `scope` field is either `"player"` (actors are player IDs) or `"team"` (actors are team IDs). Always set `"private": true` in the preset payload to hide the input prompt from non-actors. The `title` field must be a simple preset string — never a computed `formatString`.
- **Avoid Dealing Cards to Hands When Possible:** If you only need card data (digits, image URL) and not the physical card in a player's hand, use `getDeckCards(deckName)` + `selectElement` + `getObjectField` to read card fields directly from the deck — no `dealDeck` needed. This eliminates the need for `setImagesRow`. Show the card's image to the relevant player via a private `createNotification` with `cached: {image: "cardImageVar"}` instead.
- **Avoid Redundant Pre-Round Notifications:** In fast-paced round games, do not add a `createNotification` before each `selectCentralWidgetDeck`. After the tutorial, players know what to do — the repeated pop-up is noise.
- **PostHandlers:** Use `postHandlers` (e.g., `randomSelectForOneAnswerTargetVote` or `playOneRandomCard`) strictly on timed actions (actions with a `duration`) to prevent AFK stalling. Do not use them on untimed actions.
- **Conditional Duration for Disconnected Players:** Any timed action with exactly one actor should use a computed `duration` instead of a preset one: `ifElse(contains(allConnectedUsers, <actor>), <normal_secs>, 1)`. Move `duration` out of `preset` and into `computed`. Copy the pattern from Emeralds. This prevents a disconnected player from blocking the table for the full timer.

## 5. Standard Game Patterns

- **The Tutorial Sequence (required for every game):** Every game must include a tutorial. The pattern has two parts:
  1. **`beforeLoopActions`:** Show a welcome `createNotification` with the game's banner image, find the host, then trigger a `createMixVote` asking which players want the tutorial. **Always copy the `createMixVote` action verbatim from `enigma.json`** (or `emeralds.json`) — only change `backgroundColor`, `textColor`, and `borderColor` to match the current game's color scheme. Do not regenerate it from scratch. The `saveValueInCache` on this action populates `learners` (the subset who want it) and `tutorial` (boolean: `listLength(learners) > 0`).
  2. **First `gameLoop` group ("Tutorial"):** Add a group with `skipCondition: [logicalNOT(tutorial)]` containing a few `createNotification` actions (sent to `cached.to: "learners"`) explaining the rules. **The last action in this group must be an `emptyAction` with `saveValueInCache: [{name: "tutorial", value: false}]`** — this is critical so the tutorial only plays once and does not repeat on every subsequent loop iteration.
- **End of Round & Play Again:** **Always copy the end-of-round host vote (keep scores / reset / end game) verbatim from `emeralds.json`** — only change `backgroundColor`, `textColor`, and `borderColor`. Do not regenerate it from scratch.
  - Instead of hard-coding a round limit, use `gameLoopIndex` (e.g., `gameLoopIndex % X == Y`) to trigger a "Play Again?" vote every few rounds. Save the result to a `playAgain` cache variable and tie `gameOverCondition` to `logicalNOT -> playAgain`.
  - At the end of the `gameLoop`, insert an untimed "Review Round" `selectCentralWidgetDeck` action so players can see the field, then ask the host if they want to play again.
  - End the loop with an empty group containing `"checkWinCondition": true`. You do not need to manually skip actions if `playAgain` is false — the engine will naturally terminate the game.
  - **Always copy the end-of-round host vote verbatim from Emeralds** — only change `backgroundColor`, `textColor`, and `borderColor`.
- **Win Conditions & Winner Announcements:**
  - If a game is team-based, use `winCondition` (a dictionary mapping team names to boolean selectors). If individual-based, use `playersWinCondition`.
  - **Always copy the `postGameActions` notification verbatim from Emeralds** (only change `backgroundColor` and `borderColor`). It uses the engine-populated `winner` cache variable and an `ifElse` to produce `"($1) wins!"` for a single winner or `"($1) share the win!"` for ties — never hard-code a single-winner message.
- **Role-Based Team Formation with Encryptors + Fixed Clickers (Enigma pattern):** When roles need to be selected before teams are formed: (1) host uses `createVote` (type `target_point`, `allowFewerAnswers: true`, `targets: players`) to select volunteers (e.g. encryptors); (2) shuffle and `sublist` the selected group to split equally between two teams (`redEncryptors`, `blueEncryptors`); (3) `listsSubtract` to get non-volunteers, shuffle and `sublist` those too; (4) `setRole` all four groups, then compute `redTeam`/`blueTeam` via `getPlayersFromTeam`; (5) host uses two more `createVote` (type `target_point`, `answersQuantity: 1`, `targets: redTeam`/`blueTeam`) to pick fixed clickers for each team; (6) in GL-1 each round, use `nextPlayer(encryptorsList, currentEncryptor)` to rotate encryptors, and simply copy `redClicker`/`blueClicker` to `redActiveClicker`/`blueActiveClicker` since clickers are fixed. Initialize encryptors to the last element of their list before the loop so `nextPlayer` returns the first element on round 1.
- **Round Winner Feedback (Fast-Paced Games):** In short-round games, prefer sound effects and animations over `createNotification`/`highlightPlayers` to celebrate a round winner. Use an `emptyAction` with computed `sounds.list` and cached `playList.0` (targeting all players) for a broadcast sound, then `animateBox` (payload: `preset.animation name` + `cached.userIds` pointing to scoring winners) to play a named animation in the winning player's camera box. Reserve `createNotification`/`highlightPlayers` for slower games where the extra clarity is worth the extra time.
- **Spectator Management:** If allowing spectator transitions, implement `turnSpectatorToPlayerActions` and `turnPlayerToSpectatorActions` at the root. In the first `emptyAction` of BOTH sections, recompute `players` and `numPlayers` using the `allPlayers` selector (not arithmetic on the old cached value): `{"name": "players", "value": {"selector": "allPlayers"}}` and `{"name": "numPlayers", "value": {"selector": "listLength", "params": [{"name": "list", "type": "computed", "value": {"selector": "allPlayers"}}]}}`. Grant late joiners the `currentMinScore` so they don't start at 0. Place the `"turnSpectatorsToPlayers": true` / `"turnPlayersToSpectators": true` flags on a dedicated empty "Change players" group at the end of the `gameLoop`. Always end both transition sections with a `changeLayout` action to reposition remaining players correctly.
- **`orderByTeam` vs `changeLayout`:** Use `changeLayout` (type `HIGHLIGHT`, direction `VERTICAL`) when you want explicit control over which players appear on which side of the screen — teammates end up left/center/right. Use `orderByTeam` only when you are NOT using a vertical layout: it arranges the standard grid view (several rows of cameras) so teammates appear next to each other, like a typical video-conferencing platform. If you are already using `changeLayout` to group teammates, `orderByTeam` is redundant.

## 6. UI, Visuals & Audio Quirks

- **Newlines in createNotification text:** Use `<br/>` for line breaks inside `"text"` fields of `createNotification` actions. The `\n` escape does nothing and will not render as a newline.

- **Image Aliases Are Presets:** Image URL aliases defined in `gameInitOptions.images` (e.g. `"banner"`, `"winner"`, `"wallpaper"`) are string literals, not cache variables. Always reference them in the `preset` block of a payload — never in `cached`. Example: `"preset": {"image": "banner"}`, not `"cached": {"image": "banner"}`.
- **Default Player Role Avatar:** The default avatar for the `"player"` role in all games is `https://res.cloudinary.com/liars-club/image/upload/card_player_ed7jck.webp`. Always use this URL unless the game spec provides a different one.

- **No Emojis in createCard Text:** `createCard` does not support emojis. Always use plain text strings — never use emoji characters in card text fields.
- **`ratio` Field on Cards and Widget:** Both `createCard` and `createGenericCardWidget` accept an optional `ratio` field in their `preset` payload that overrides the card's aspect ratio. For `createCard`, `ratio` is a **float** (e.g., `1.6`). For `createGenericCardWidget`, `ratio` is a **string** (e.g., `"1.6"`). In practice, adding `ratio` tends to distort the layout and make cards look worse — omit it unless the spec explicitly requires a non-default aspect ratio.
- **Summary-Card Column Pattern:** When a game needs players to see a text summary (e.g. clues) alongside clickable position decks in a widget, add a dedicated non-clickable "summary" deck per team as the first column (e.g. `red_clues`, `blue_clues`). After all relevant inputs are collected, place one `createCard` per team into those decks with a formatted summary text. Update `createGenericCardWidget` dimensions to `[rows, columns+1]` and prepend the summary deck names to the `decks` list. The summary decks are NOT listed in `selectCentralWidgetDeck` — they are display-only. Create them with `counter: false` so no card count badge shows.
- **UI Grids:** When generating a `GenericCard` Widget, the `dimensions` array format is `[rows, columns]`. For trick-taking games, use `[2, numPlayers]` — 2 rows, N columns (one per player). The easy mistake is to reverse this to `[numPlayers, 2]`. Set the widget decks to `facedown: true` and set the label to the owning player's name.
- **setImagesRow and Card Hand Space:** Use `setImagesRow` with a transparent image only when players hold a card hand that opens from the bottom of the screen, so the hand doesn't collide with the central widget. If players have no hand (e.g. Buffalo), omit `setImagesRow` entirely. Heights: `maxHeight: 140` for normal-sized hands; `maxHeight: 230` when `"increaseHandHeight": true` is set in `visualSettings`. You cannot set `maxHeight` to 0 — use `10` to visually clear it at end of game.
- **Hand Visuals:** If players hold very few cards, set `"increaseHandHeight": true` in `visualSettings` and set `"maxHeight": 230` in the `setImagesRow` action.
- **Audio Arrays (playList):** Every action that plays a sound requires ALL THREE fields together or the sound will not play correctly: `sounds.list` (array of soundboard aliases, in `preset`), `sounds.waitForSoundEnd` (boolean, in `preset` — `true` to block until sounds finish), and `playList.X` (list of player IDs to receive the Xth sound; in `cached`, referencing the `players` variable — e.g. `"cached": {"playList.0": "players"}`). Use `playList.0` to send all sounds in `sounds.list` to the same audience. Missing any one of these three fields means the sound does not reach its targets. Do NOT use `allUsers` for `playList.0` — use `players` (spectators don't need sounds directed at them explicitly).
- **drawArrows:** This action visually shows one player pointing to another. The `computed` payload requires a dictionary where the keys are the origin player IDs and the values are lists of target player IDs.
- **gameInitOptions Timing Fields:** Use exactly one of `time`, `timePerPlayer`, or `timePerRound` (integers, in minutes). `time` = total game duration constant regardless of player count. `timePerPlayer` = scales with player count. `timePerRound` = duration of a single round, minimum value 1 (use for round-based games like Buffalo). Never include more than one timing field.
- **Always Use Spec Assets:** When a spec provides URLs for wallpaper, banner, and animations, always use them verbatim in `gameInitOptions.images` (wallpaper, banner) and `gameInitOptions.animations`. Never substitute placeholder or default URLs.

## 7. Trick-Taking Games

- **Ordinal Roles for Trick Order:** In trick-taking games, use fake ordinal roles ("1st", "2nd", "3rd", "4th") to show each player their position in the current trick order. Define the roles in `gameInitOptions.roles` and add them to the team's `roles` array. Cache an `ordinal` dict (`{"0": "1st", "1": "2nd", ...}`) in `beforeLoopActions`. At the start of each trick, run a `parallel` group ("Show Order") that calls `showFakeRole` for each player: compute each player's ordinal as `getCachedObjectValue(ordinal, remainder(numPlayers + spaIndex - indexOf(players, trickLeader), numPlayers))`, and set `from` to `createList(players[spaIndex])`. This pattern is taken directly from Emeralds.

- **Standard Wood Background:** Unless otherwise specified, set `"cardBackgroundImage"` in `visualSettings` to `https://res.cloudinary.com/liars-club/image/upload/wood_qbegm0.jpg` (styles the player's card hand), and set `"backgroundImage"` in the `createGenericCardWidget` preset payload to the same URL (styles the central widget). Used in essentially all trick-taking games.
- **Spectator→Player: Rebuild Player-Specific Content:** When a spectator becomes a player, `turnSpectatorToPlayerActions` must rebuild any player-specific labeled decks or cards that were created for the original player set. Compute the new player's index with `indexOf(players, newPlayer)`, use it to identify which slot they occupy, re-label the deck for that slot, clear old cards, and create fresh content for the new player. Use the new player's index everywhere `repeatIndex` would be used in the normal round flow.

- **Card Play Location:** The cards in each trick should be played to the central widget unless the central widget is needed for something else (e.g. the ladder in Pecking Order), in which case cards should be played to players' videoboxes.
- **Bidding UX:** If the game involves bidding, typically give each player a `createVote` action to declare their bid, then put bid cards in each player's videobox to visually track progress. Some games warrant a different approach depending on whether bids are discrete values, ranges, or sequential.
- **`updateScore` Payload Structure:** `scores` is an array of entry objects. Each entry has `list` (array of player IDs), one of `score` (set to value) or `delta` (add to current), and optionally `secondScore: true` (boolean) to target the second score display. Omit `secondScore` to target the first score. To update both scores, use two separate entries (or two separate `updateScore` actions). Never set `secondScore` to an integer — it is always a boolean flag. Never initialize scores to 0 — they start at 0 by default.
- **Reset secondScore Every Round Unconditionally:** If the second score tracks a per-round stat, reset it to 0 at the end of every round regardless of whether the host chose to reset main scores. Put the secondScore `updateScore` (score: 0, secondScore: true) in the unconditional End Round group, not in the conditional Reset Scores group.
- **`nextPlayer` Selector:** Takes exactly two params: `playersList` (type `cached`, the full players list) and `playerId` (type `cached`, the current player ID). Returns the next player ID in the list after `playerId`, wrapping around. Do not use `players` or `current` as the param names.
- **Player-Count-Dependent Card Sets:** Name player-count-dependent sets by their integer count (`"3"`, `"4"`, etc.). Then in `createDeck`, pass `numPlayers` directly as the `set` value via `cached` — Ludio converts the integer to a string to look up the set name, eliminating any `ifElse` branching.
